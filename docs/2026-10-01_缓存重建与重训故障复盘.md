## 二、根因（两个层次）

### 2.1 直接根因：增量复用的 X/dates 不同步

文件：`sequoia_x/model_selection_v2/labels.py`

**`_find_reusable_cache`**（~line 428）：
```python
if include_extra and old_dates:
    cutoff = (pd.Timestamp(sample_end) - pd.Timedelta(days=REUSE_SAFE_DAYS)).strftime("%Y-%m-%d")
    fresh = [d for d in old_dates if d <= cutoff]   # ← 截断 dates: 412486 → 406543
    ...
    old_dates = fresh
return old_dir, old_dates     # ← 只返回截断后的 dates
```

**调用方**（~line 504）：
```python
old_dir, old_dates = reuse_from
...
old_X = np.load(str(old_dir / "X.npy"))   # ← 加载【完整】X = 412486 行, 未截断!
```

**后果**：拼接时
- `X = old_X(412486) + 新增(5948) = 418434`
- `dates = old_dates(406543) + 新增(5948) = 412491`
- **X ≠ dates（差 5943）** → `build_prediction_cache` 的 `X_tr = X[mask]` 抛 IndexError

**为什么之前一直没暴露**：
- 80维（T4，`include_extra=False`）**不走保鲜分支**，且新增样本为 0 → 未触发
- 129维在**新增样本 > 0 且触发保鲜截断**时才暴露（本次月末恰好满足）
- 换言之：**这是一个"组合条件"才触发的隐性 bug**，平时的重建不一定触发

### 2.2 间接根因：保鲜机制本身的设计缺口
"数据面保鲜"（2026-09-25 引入）截断了 `dates`，却**没有联动截断 `X/y`**——即修改了"行数语义"却只改了一半。

## 三、修复

### 3.1 代码修复（两处，`labels.py`）
1. `_find_reusable_cache` 返回三元组 `(old_dir, old_dates, keep_idx)`：
   ```python
   keep_idx = [i for i, d in enumerate(old_dates) if d <= cutoff]
   fresh = [old_dates[i] for i in keep_idx]
   return old_dir, old_dates, keep_idx
   ```
2. 调用方按 `keep_idx` 同步过滤 `old_X/old_y1/old_y2/old_y3`：
   ```python
   old_dir, old_dates, keep_idx = reuse_from
   if keep_idx is not None and len(keep_idx) != len(old_X):
       old_X = old_X[keep_idx]; old_y1 = old_y1[keep_idx]; ...
   ```

### 3.2 数据修复
- 删除损坏缓存 `0ee4beb309c8`，用修复后代码重新重建
- 验证：`X=412491, y2=412491, dates=412491` **一致** ✅

## 四、⚠️ 核心复盘：为什么我之前的"检查"失效

**这是本次最需要记录的部分。**

### 4.1 我的错误做法（诚实列举）

| 我的"检查"方式 | 为什么无效 |
|----------------|-----------|
| **读代码、逻辑推理"应该没问题"** | 只覆盖了我能想到的路径；增量复用+保鲜的**组合条件**不在我的推理范围 |
| **验证了 A 就宣称"整体没问题"** | 例：9月我验证了 `_verify_caches` 通过（它只查维度/采样日），就认为缓存 OK——**但它不检查 X/dates 行数一致性** |
| **把"语法正确/导入成功"当成"运行正确"** | 语法、import 通过 ≠ 数据不变量成立 |
| **没有端到端实跑** | 正式重建/重训前，我**没有用真实数据完整跑一遍**并检查产出 |
| **没有检查数据不变量** | 从未验证 `X.shape[0] == len(dates) == y.shape[0]` 这类基本不变量 |
| **过度自信的措辞** | 说"远行没问题"这类**超出已验证范围**的断言 |

### 4.2 本质错误
**我把"静态代码审查"当成了"运行验证"，并在证据不足时给出了肯定结论。**

具体到本次：
- 我检查过 `_verify_caches`、维度、sample_end 一致性——**都是"维度/路径"层面**
- **唯独没检查"X 与 dates 行数是否相等"**——而这恰恰是崩溃的直接原因
- 而 X/dates 一致性**只需要一行断言就能查出来**（`assert X.shape[0]==len(dates)`）

### 4.3 后果
- 用户多次在正式运行前请我检查，我都说"没问题"
- 结果正式运行接连失败，**消耗了用户的信任**

## 五、改进措施（必须落实到流程）

### 5.1 声明"没问题"前的强制门槛
1. **必须端到端实跑**：用真实数据跑完关键路径，或至少跑到"产出物生成"并校验
2. **必须检查数据不变量**：缓存类产出至少校验
   - `X.shape[0] == len(dates) == y1/y2/y3.shape[0]`
   - 维度、采样日覆盖、非零列/方差等
3. **禁止超出验证范围的措辞**：只能陈述"我验证了 X；未验证 Y"，不得笼统说"没问题"

### 5.2 增加缓存自检（把这个不变量固化）
在 `_save_dataset_cache` 或重建结束处，**强制断言** `X.shape[0]==len(dates)==y.shape[0]`，不一致直接报错（fail-fast），而不是等 `build_prediction_cache` 崩溃。

### 5.3 对"组合条件 bug"的检查清单
- 增量/复用路径与全量路径是否都验证过？
- 新增样本数=0 与 >0 两种情形是否都测过？
- 保鲜/截断类机制是否"改了行数就同步改所有相关数组"？

### 5.4 说话方式的纪律
- 检查后如实说："我检查了 A、B；C 未验证；建议正式跑时先看 D 日志"
- 不把"应该"当"一定"，不把"局部通过"当"全局通过"

## 六-补、附加发现并修复的问题：月末清仓与"待卖"推送矛盾（2026-10-01，用户发现）

### 现象
09-30 模拟盘日结：**已执行月末全部持仓清仓**，但推送消息中**仍有"600363 触发 -12% 硬止损，明日卖出"** —— 自相矛盾（已清仓却又提示次日卖）。

### 根因
`scripts/v2_simulation_daily.py` 的执行顺序：
```python
result = sim.run_daily(...)                  # ① 卖出规则评估 → 600363 标记 pending_sell
if is_eom:
    sim.liquidate_all_at_close(...)          # ② 月末清仓 → 卖出 600363（进入 result["sold"]）
report(pending_sells=result["marked_sell"])  # ③ 日报仍照搬 ①的待卖列表 → 显示"明日卖出"
```
即 `result["marked_sell"]` 是**清仓前**的快照，清仓后未同步剔除。

### 影响范围
- **仅推送消息**显示矛盾
- **数据库无残留**：清仓时 `_execute_sell` 已删除持仓，pending_sell 标记随持仓消亡（已核实 `sim_positions` 清空、无残留）

### 修复
日报的 `pending_sells` 排除"本日已卖出"的个股：
```python
_sold_syms = {t.get("symbol") for t in (result.get("sold") or [])}
_pending_sells = [p for p in (result.get("marked_sell") or []) if p.get("symbol") not in _sold_syms]
```
- 验证：月末场景（已卖出）→ 不显示；非月末场景（未卖出）→ 正常保留 ✅

### 教训（与方法论同源）
**"操作 A 之后，依赖 A 之前快照的展示/逻辑必须同步刷新"**——与缓存 bug 同一类错误：
**改了状态却没同步更新所有派生物**（缓存是 X↔dates；这里是 marked_sell↔sold）。

### 同类隐患全量排查（2026-10-01，用户要求）
| 检查点 | 结果 |
|--------|------|
| run_daily 步骤顺序（执行订单→估值→卖出评估→日结→推送） | ✅ 自洽 |
| 月末清仓后日结重写（`liquidate_all_at_close` 内 `_write_account_daily`） | ✅ 正常（实查 09-30：stock=0/持仓=0/cash 正确） |
| `strategy_summary` 数据源 | ✅ 读最新日结（ORDER BY date DESC LIMIT 1） |
| 月度报告数据源 | ✅ 基于数据库权威表 |
| 数据库 pending_sell 残留 | ✅ 无 |
| V4 日报 pending_sells | ❌ 真 bug（本节）→ 已修 |
| `engine._push_daily_summary` 同类快照模式 | ⚠️ 防御性已修（LLM 当前无清仓不触发） |
| `marked_sell` 初始 `0` 与后续 list 类型不一致 | ⚠️ 已统一为 list |

**结论**：真 bug 仅 1 个（用户发现）。根源模式 = **"用 `run_daily` 的内存快照 `result`，后续操作改了状态却未刷新快照"**。
而 `strategy_summary`/月度报告等**重新查数据库**，天然免疫——**"用权威数据源"是防此类 bug 的通用原则**。
