## 二、真问题：防追高闸门在 024 路径上**静默失效**（已修）

### 现象

10/8 管线日志两行警告：

```
WARNING signal_day_return(000651) 查询失败: no such table: stock_daily
WARNING signal_day_return(601318) 查询失败: no such table: stock_daily
WARNING 追高过滤: 2 只当日涨幅不可得，按原逻辑放行: ['000651', '601318']
```

### 根因（台账库与行情库分家，但代码仍"一个参数走天下"）

- 2026-09-25 加的**防追高闸门**：信号日涨幅 > 6% 的标的不生成买入信号
  （依据是"LLM 买入即跌"归因：选中组涨停占比 27% vs 淘汰组 12%，追高组 10 日超额转负）。
- 它需要**行情**（`stock_daily` 表）。老 004 路径里，台账库和行情库**是同一个库**（主库），
  所以 `filter_chase_risk(db_path, ...)` 用一个参数没问题。
- 024 把**台账挪进了独立库**（`sim_hs300.db`），行情仍在 004 主库 —— 但调用时只传了台账库路径，
  于是 `stock_daily` 查不到 → 抛 `no such table` → 被 `except` 吞掉 → **fail-open（放行）**。
- **危险点**：它不崩、不报错、信号照写，只在日志里留一行 WARNING ⇒ 属于**静默失效**，
  与 9/25 那批"接线错误"（实盘跑错信号源、几个月没发现）同一类。

### 修复（3 处，最小改动）

| 文件 | 改动 |
|---|---|
| `sequoia_x/simulation/signals.py` | ① `save_llm_recommendations()` 新增 `price_db_path` 参数（默认 None = 与 `db_path` 同库，004 原行为不变）；② `signal_day_return()` 把"表不存在"从"警告+放行"改为 **`RuntimeError` 直接报错**（表不存在＝传错库，属配置错误，不是数据缺失；单只股票缺行仍照旧 fail-open） |
| `024_llm_hs300/scripts/main_hs300.py` | 新增 `SOURCE_DB` 常量（004 主库绝对路径），调用时显式传 `price_db_path=SOURCE_DB` |
| `tests/test_chase_filter.py` | 补 2 个回归测试：台账库/行情库分离时必须过滤生效；传错库必须抛错 |

### 验证（4 项，全部通过）

1. **单测**：`pytest tests/test_chase_filter.py` → **9 passed**（7 旧 + 2 新）。
2. **真实数据**：用 10/8 真实行情跑过滤 —— 抽样的 6 只涨幅 >6% 的股票（300522/688196/301697/300530/301513/300619，+17.6%~+20%）**全部被剔除**，000651/601318 保留 ✅。
3. **原路径回归**：不传 `price_db_path`（004 老调用方式）时行为不变（+10% 的 AAA 被剔除、+3% 的 BBB 写入）✅。
4. **调用点审计**：全仓只有 2 个调用点（004 `main.py`=老盘入口、024 `main_hs300.py`）——前者传的就是主库、后者已修；024 的 `SOURCE_DB`/`SIM_HS300_DB` 实跑解析到真实文件 ✅。

### 本次有没有造成损失

**没有**。10/8 推荐的两只当天涨幅 **+0.10% / −1.16%**，都不到 6% 阈值，闸门就算工作也是放行。
所以这次是"保险丝断了但没短路"——已修好，且**原来的待买信号无需取消**。

**为什么清**：老 LLM 盘（`main.py`，8 策略 → LLM）10/1 起被 024_llm_hs300 取代，
004 管线已无它的步骤，但 4 张表还留在主库 —— 容易被误当成"在跑的盘"
（本次复盘就踩到：日报数字被误读成新产生的）。

**前置审计（确认无活引用）**：V2/V4 盘台账在 `sim_v2.db`、LLM-HS300 台账在 024 的
`sim_hs300.db`、004 管线无 `main.py` 这一步 ⇒ 主库这 4 张表只有**历史复盘脚本**
（`experiments/llm_sim_diag/*.py`、`scripts/redo_sim_20260923.py` 等）在读。

**执行**（`scripts/archive_retired_llm_sim_20261009.py --execute`，可重跑、默认 dry-run）：

| 表 | 行数 | 归档后主库 |
|---|---|---|
| sim_positions | 11 | 0 |
| sim_closed_trades | 93 | 0 |
| sim_account_daily | 62（2026-07-02 ~ 09-30） | 0 |
| sim_buy_signals | 122 | 0 |

- 归档库：`data/archive/sim_llm_004_retired_20260930.db`（84 KB，含 `archive_meta` 说明）
- **校验方式**：逐表"行数 + 全表逐行 md5"比对，4 张表**完全一致**后才执行删除；
  删除后 4 张表均为 0 行、主库 `PRAGMA quick_check = ok` ✅
- **未 VACUUM**：1.8 GB 主库 VACUUM 会长时间独占锁、影响正在跑的回测；删的只有 ~290 行，
  空间意义可忽略。

  逐项复核无变化；当时在跑的 3 个 V6-A 回测未受影响。

**要复现历史分析怎么办**：把 `experiments/llm_sim_diag/*.py` 等的库路径从
`data/sequoia_v2.db` 指向 `data/archive/sim_llm_004_retired_20260930.db` 即可（表名、列完全一致）。

## 四、遗留提醒

1. **汇总里的对比口径**：10/8 那句"V4 领先 LLM-HS300 +4.34%"是**不公平对比**——
   V4 背着 8 月以来的两个月历史、HS300 是 10/8 才开账。等 HS300 攒够天数再看才有意义。
2. **老 LLM 盘代码仍在**：`main.py` 的老 LLM 链路未删除（只清了它的数据）。
   若要彻底归档代码，需另评估（`sequoia_x/simulation/*` 是三个盘共用的，不能整包删）。
3. **同类风险点自查口径**（本次教训的通用形式）：**台账库/行情库分家后，
   任何"顺手用台账库路径查行情"的代码都会静默失效**。新增独立台账库的盘时，
   必须把"行情从哪读"显式传参、并让**配置错误 fail-loud**（本次已示范）。
