# 回测 IC 异常排查清单（2026-09-26）

## 现象

生产预测缓存（V5，70 个月）的 T2 预测，对**下一个月已实现的 20 日超额收益**的
Rank IC = **+0.2304**，ICIR 1.29，**99% 的月份为正**。

**这个量级在真实市场不成立。** 同一片数据、同一套 y 口径下的朴素信号：

| 信号 | 均值 IC | ICIR |
|---|---|---|
| **生产预测缓存** | **+0.2304** | **1.288** |
| 20 日动量（无未来信息） | −0.0444 | −0.337 |
| 60 日动量 | −0.0649 | −0.468 |
| 5 日反转 | −0.0348 | −0.359 |
| 随机数 | +0.0018 | 0.095 |

**⇒ 强烈指向某处存在未被发现的前视偏差。**

> ⚠️ **在查清之前，本项目的回测数字（V4 的 +2077%、V5 的 +10081%、以及 8/21 基准）
> 都不应对外引用。** 今天"V5 比 V4 好 4.9 倍"的结论已撤回。

## 已确认存在、但**不足以解释**的泄漏

**训练标签跨入预测期**：训练窗口截止 `train_end`（前一月末），而最后 1~2 个采样日
（如 2026-05-26）的标签 y2 = 其**之后** 20 个交易日的收益 ≈ 2026-05-27~06-24，
**落进被预测的 6 月**。`MAX_TRAIN_SAMPLES=5000` 使训练集只剩最后 ~1.8 个采样日
→ **100% 的样本都在泄漏**。

**但实测其量级只有 ~0.04**（见 `experiments/attribution_4x/purge_test.py`：
leaky 档 0.04/0.02/0.09/0.07/−0.02/0.09）。**解释不了 0.23。**

> 推测：harness 的几何与生产不同 —— harness 在**采样日**预测、隔约 15 天评估，
> 泄漏窗口与评估窗口重叠小；生产在**月末**预测、评估整个下月，重叠大。
> **故必须在下述 P0-3 用生产几何重测。**

## 排查清单（按「最可能 × 最便宜」排序）

### P0 —— 先分清"测量问题"还是"管线问题"（合计 ~40 分钟）

**P0-1 用 ic_compare 的口径评估 harness 的预测**（~10 min）
- 做法：取 harness 对某采样日的预测，用 ic_compare 同款 y（该日后 1~20 交易日超额收益）算 IC
- 判据：若 harness 预测在该口径下也跳到 0.2+ → **是我的评估口径问题**；若仍是 0.05 → **是管线问题**
- 这是最关键的一刀，**先做它**

**P0-2 用采样日口径评估生产缓存**（~5 min）
- 做法：把生产缓存里某月的 t2 与该月**首个采样日**的后续 20 日收益对齐算 IC
- 判据：若从 0.23 掉到 0.05 → 差异来自「月末 vs 采样日」的几何

**P0-3 ★ 在生产几何下做 purge（决定性，~40 min）**
- 做法：改 `build_prediction_cache` 的训练 mask，把上界从 `train_end` 提前到
  `train_end − 25 交易日`（保证标签完整），重跑 ~15 个月，用 ic_compare 口径算 IC
- 判据：**若 IC 从 0.23 掉到 ~0.05 或更低 → 泄漏即全部原因**；若仍是 0.2 → 另有来源
- 这是唯一能在**生产几何**下量化该泄漏的实验

### P1 —— 特征层前视（若 P0 指向管线）

**P1-1 逐组零掉扩展特征，看 IC 掉多少**（~30 min，可复用 D0 harness）
- 8 组分别置零：fund_flow / finance / holders / consensus / news / xdxr / dragon_tiger / limit_up
- 判据：若某组一去掉 IC 就从 0.23 崩到 0.05 → **该组在送分**，重点查
- 注意：`consensus` 已知恒 0、`news/dragon_tiger/limit_up` 仅近端有值，优先查
  **`finance`（16 维）与 `fund_flow`（6 维）** —— 它们全期覆盖

**P1-2 as-of 对齐审计**（阅读 + 抽样，~30 min）
- 逐个检查 `build_extra_features.py` 里各组的**日期落点**：
  - `_finance_features`：按**披露日**还是**报告期**对齐？（若是报告期 → **典型前视**）
  - `_fund_flow_features`：东财日频资金流是否有提前/滞后
  - `_news_features` / `_dragon_tiger_features` / `_limit_up_features`：用**发布日**还是事件日
- 依据：CLAUDE.md 自己记着 roadmap「finance 切官方 API（+**精确披露日**）」——
  **说明现用口径的披露日并不精确**，这是首要嫌疑

**P1-3 日期平移检验**（~20 min）
- 做法：把可疑组的特征整体**后移 N 天**（只允许用更早的数据）后重训
- 判据：若 IC 显著下降 → 前视确认；若不变 → 该组不是来源

### P2 —— 训练/样本层

**P2-1 训练集与评估集的行对齐**（~15 min）
- 检查缓存里 `X[i]` 与 `y2[i]`、`dates[i]` 是否严格同源（在 `labels.py` 的拼装处逐行核对）
- 判据：若 X 的窗口末尾与 y2 的起点错位 k 天 → 模型在"预测过去"

**P2-2 归一化的作用域**（~15 min）
- `features.py:429` 的 Z-score 用**传入 df** 的均值/方差。确认所有调用点的 df 都已截到 ref_date
- （已抽查 `build_stock_features` 与 `_build_one_features` 均截断，但**需全量核对调用点**）

### P3 —— 兜底

**P3-1 完全独立复现**（~1 h）
- 不重用任何项目代码：从 DB 直接算特征 → 训一个 LightGBM → 算 IC
- 判据：若独立实现也给 0.23 → 数据本身有问题（价格/标签）；若给 0.05 → 项目代码有 bug

## 我的下注

1. **首选：`_finance_features` 按报告期而非披露日对齐** —— 财报公布滞后 1~3 个月，
   按报告期落轴 = 每个样本都能看到"未来"的基本面。这能轻易造出 0.2+ 的 IC，
   且**对全部 70 个月都成立**（与"99% 月份为正"吻合）。
2. **次选：P0-3 的生产几何泄漏** —— 若重叠比我估算的大，也可能撑到 0.2。

**第一个该做的实验是 P0-3**（唯一能在生产几何下判定），**其次是 P1-1**（能直接指认哪组特征）。
