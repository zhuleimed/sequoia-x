> 起因：LLM 模拟盘归因诊断（见 `2026-09_LLM模拟盘买入即跌归因诊断.md`）顺藤查出日线数据问题，
> 再往下一层核查 **V4 训练缓存本身**，发现特征管线还有 3 个**不报错、只静默污染训练**的结构性问题。

## 一、体检方法（可复现）

判断"某一维特征是否携带信息"，用**连续块读 + 逐列零方差**，而不是读代码或看文档：
在一次采样里，只要某列恒为常数，就会被 `features.py:393` 的零方差保护**精确清成 0**，
故"全零列"就是"死列"的可靠指纹。

```python
import numpy as np
X = np.load('data/cache/v2_dataset/<hash>/X.npy', mmap_mode='r')
blk = np.asarray(X[-300:])                     # 取**连续块**（随机 fancy-index 在 24GB 文件上很慢）
zero_cols = [i for i in range(X.shape[2]) if (blk[:, :, i] == 0).all()]
```

⚠️ **必须取连续块**：`dates.json` 与 `X.npy` 行序对应，早期块与近期块的数据可用性不同
（`news`/`dragon_tiger`/`limit_up` 只有近一年的事件），只抽一个块会得出片面结论。
早期块与末块**都要看**。

### 实测结果（生产缓存 `533295829c0e`：129 维 / 399,775 样本 / sample_end=2026-08-21）

| 位置 | 维数 | 内容 |
|---|---|---|
| `16, 17` | 2 | `turnover_rate` / `amount_ratio`（amount/turnover 当时全 NULL → 填 0） |
| `37~52` | 16 | §6 大盘关联(6) + §6b 市场状态(8) **全部走 fallback 零**，加上布局错位残留 |
| `102~106` | 5 | **consensus 全组** |
| `111, 112` | 2 | xdxr 的 `xd_div_cnt_3y` / `xd_song_cnt_3y` |
| `119~128` | 10 | padding（补零到 129） |

**共 35 列零方差**。独立佐证：`data/feature_importance_v4.json`（2026-08-21）里
`xdxr` / `dragon_tiger` / `limit_up` 组增益**均为 0.0**。

## 二、三个结构性问题

### 问题 1：§6 分支不对称 → 列语义整体错位 2 列（最严重）

`features.py` 的 §6 大盘关联段：`if`（指数可用）追加 **6** 维，`else` 追加 **8** 维零。

而"指数是否可用"是**逐股**判定（`len(df_index) == n`）——当前 DB 下仅 2,385/5,202 只等长。
**一次重建会让同一个 X 里同时存在两套列布局**，§7 之后所有列相差 2 位，
即"同一列在不同样本里含义不同"，且**不会报错**。

**为什么"8"是错的**：模块 docstring、`BACKTEST_PLAN.md:81`、设计文档
`docs/superpowers/specs/2026-07-23-model-selection-v2-design.md:128` 都写"大盘关联 8 维"，
但设计文档**实际只命名了 6 个**特征（指数收益率 / 20日Beta / 相对强度 /
指数MA20、MA60 位置 / 近5日超额），与代码 `if` 分支**逐一对应**。
→ "8"是文档记账错误，`else` 照着错的数字补了 8 个零。

**修法**：统一为 6；新增 `BASE_FEATURE_DIM = 68` 常量并在 padding 前**加断言**，
列数不符即抛错。回归测试 `tests/test_feature_layout.py`（6 项）锁死该不变量。

### 问题 2：训练/推理取指数走散 → 推理时 14 维恒 0

- `labels.py`（训练侧）：查 `index_daily`（`sh.000300`）→ 回退 `stock_daily`（`000300`）✅
- `features.py`（推理侧）：用 `engine.get_ohlcv("000300")`，而
  `DataEngine.get_ohlcv`（`data/engine.py:167-174`）**只查 `stock_daily`** ——
  指数根本不在那张表里 → 恒返回空 → `df_index=None` → §6+§6b **共 14 维在预测时永远为 0**

这类差异**不会报错**，只会静默产生恒 0 特征。

**修法**：新增 `sequoia_x/model_selection_v2/index_source.py`，统一两处的表名与回退规则
（含前视变体 `load_index_close_forward` 供标签侧使用）。

### 问题 3：扩展特征死列 + 缓存复用不感知数据刷新

| 子问题 | 位置 | 说明 |
|---|---|---|
| `xd_div_cnt_3y` / `xd_song_cnt_3y` 恒 0 | `build_extra_features.py::_xdxr_features` | 原为**整列单一标量** → 必被零方差保护清零；且 `song` 用的是**全历史**次数（语义也不对） |
| `xd_yield` 近乎死列 | 同上 | 原按**事件日** reindex → 只在除权当天有值（实测 1,733 交易日仅 14 天非零） |
| consensus 生效日不可靠 | `_consensus_features` | 原读**文件 mtime** 当"快照生效日" |
| 复用不感知数据刷新 | `labels.py::_find_reusable_cache` | 等价判据只含参数 hash、**不含数据状态** |

**关于 consensus 的一处澄清**：把"快照采集日**之前**"的样本掩掉**是正确行为**——
快照当时还不存在，拿它当历史特征就是前视偏差。所以"老样本上 consensus 为 0"不是 bug。
真正的 bug 是**判断"采集日"的依据错了**：mtime 是文件系统元数据，会被复制 / rsync /
重写 parquet / 重新下载任意改写，一次不经意的文件操作就能把生效日整体挪位，
而且不报错（实测同一份数据，mtime 为 8/31 时"全 0"、为 8/7 时"有值"）。

**修法**：
- xdxr 两列改**逐日 as-of 滚动计数**（`avail ∈ [d-1095d, d]`），`xd_yield` 改 as-of ffill 对齐
- consensus：采集时写 `snapshot_date` 列（属数据本身、随文件走、刷新不改写），特征侧优先读它
- 复用加**保鲜边界** `REUSE_SAFE_DAYS=60`（> 采集刷新窗口 40 天）：近端一律重算

## 三、日线数据问题对 V4 的影响（量化）

生产缓存 `533295829c0e` 建于 2026-09-01，**早于本轮数据修复**，故三个数据问题都在里面：

| 问题 | 对 V4 的影响 |
|---|---|
| 深市 2024-01-02~2026-06-08 存**后复权价** | ① 窗口跨边界的样本特征含巨大假值（2024-01-02 假涨中位 +127%、2026-06-09 假跌 -55.9%）；② `apply_adjust` 会**再套一层后复权**（双重复权）；③ **水平类特征**（`amount_ratio`、`vol_corr` 与价格水平的相关）在段内被每股复权因子 K 扭转（K 中位 2.46）；④ 仅深市（占基础池 46.8%） |
| `amount` 缺失 76.6% | `amount_ratio = amount/(close×1e8)` 缺失 → NaN → `nan_to_num(nan=0)` → **恒 0**，把"未知"编码成"成交额为 0" |
| 2026-07-06/07-07 单日错乱 | 窗口/标签跨越该两日的样本（量级小） |

**受影响样本比例**（按缓存 399,775 样本实算）：
窗口跨 2024-01-02 边界 40,026（10.0%）、跨 2026-06-09 边界 8,795（2.2%）、
段内 170,982（42.8%）。

## 四之二、已知未修项：训练股票池是"今天的快照"，不是逐日动态 ★登记待办

> 2026-09-25 核查时发现并登记。**本轮不修**（改的是"股票池构造"本身，影响面大于前几项，
> 需要先定口径），留作下一版独立课题。

### 现状（代码事实）

`labels.py:466-467` **只调用一次** `engine.get_base_stock_pool()`，
`labels.py:511-512` 把**同一个 symbols 列表**喂给全部 148 个采样日；
`n_stocks` 是缓存 hash 里的**单一数字**。整个 `labels.py` grep 不到任何
"停牌 / 涨跌停 / 一字板"过滤。

**即：2,978 只对全部采样日是同一份固定名单，不存在逐日动态变化。**

`get_base_stock_pool()` 的过滤条件及其**时间口径**：

| 条件 | 实现 | 时间口径 |
|---|---|---|
| 非北交所/科创/创业 | 按代码前缀 `688/689/300/301/4xx/8xx` | ✅ 静态，全历史一致 |
| 非 ST / 非退市 | `"ST" in name or "退" in name` | ⚠️ **今天的股票名** → 全历史一刀切 |
| 非次新（上市满 1 年） | `ipo_date > today - 365d` | ⚠️ 用**今天**比 → 全历史一刀切 |
| 股价 > 2 元 | 最新收盘价 | ⚠️ 用**今天**的价 → 全历史一刀切 |
| 非停牌 / 非涨跌停 | — | ❌ **无此过滤** |

### 两个真实的方法学问题

**① 幸存者偏差**：`query_stock_basic` 里 `status != "1"`（已退市）直接跳过
→ 训练集只含"活到今天"的股票，历史上退市的那批从未进入训练。
（且 `stock_daily` 里退市股已被 `_archive_delisted_stocks` 移到 `stock_daily_archive`，
即使想去捞也要额外取数。）

**② 用今天的信息筛选历史样本（look-ahead）**：
- 今天被标 ST 的股票，从**全部历史**被剔除 —— 哪怕 2020 年它还正常
- 反之，今天非 ST 但历史上是 ST 的，那些 ST 期间照样当正常样本用
- "今天股价 1.8 元"的股票从全历史剔除 —— 哪怕 2020 年它是 20 元

### 下一版建议方向（待定口径）

- 按 `date` **逐日重放**板块/ST/次新/价格过滤（ST 需要历史名称表，当前无此数据源，
  可能要用 `stock_list` 的历史快照或从公告/行情特征推断）
- 明确决定**是否纳入已退市股票**（纳入则需从 `stock_daily_archive` 取数）
- 补上"非停牌 / 非涨跌停（不可成交）"的逐日过滤 —— 这与回测的成交假设直接相关
- 以上都会改变训练集规模与构成，**建议单独立项、单独评估**，不要与其他改动混在一起

1. **别信手抄的列名清单**：`scripts/analyze_v4_feature_importance.py` 自带的 `EXTRA_COLS`
   与实际列序不一致，一度导致"consensus 有增益"的误判。**判列序用实测探针**。
2. **缓存复用会冻住旧数据状态**：`_find_reusable_cache` 让 8/21 的旧行整块搬进 9/1 的缓存
   （实测两个目录的 `dates.json` MD5 相同、抽样 `X.npy` 逐字节相同），
   任何 `data/extra_features/` 刷新都进不到旧采样日。
3. **训练/推理必须同源**：同一件事（取指数）在两处用了不同的表名，
   不报错、只静默产生恒 0 特征。
4. **文档与代码不一致时，以"能被证据支持的一方"为准**：§6 的"8 维"三处文档都这么写，
   但设计文档实际只命名 6 个特征——**"8"是记账错误**。若照文档去"补 2 维"，
   就会凭空发明特征。
